# REVIEW.md — правила ревью для startup-trainer-pilot-v1

Читает ревьюер: Claude (`/code-review`, `/security-review`, GitHub Action) и человек.
Основание: Q-067 (решение Бориса 17.10.2026), эталон — Anthropic «How the Claude Code team does code review», 15.10.2026.
Короткий файл намеренно. Повторяющееся замечание ревью → новая строка здесь, а не в каждом PR.

## 1. Что в этом репо считается провалом (ищи это в первую очередь)

1. **PASS без прогона.** Слова «PASS», «12/12», «приёмка пройдена», «готово» без лога pytest или команды с выводом в описании PR. Самопроверка автора ≠ приёмка (Р-7, Д-42; случаи: HQ-023 ред. 1, PF-14).
2. **Статус выше доказательства.** Код ставит «факт», VERIFIED, «подтверждено», SENT, DONE при уровне ниже E3 или без подписи по Р-5/Д-41. Статуса «факт» без подписи нет.
3. **Порог или правило не из канона.** Число-порог (runway, свежесть данных, балл, вес) в коде должно совпадать с каноном и иметь ссылку на Д-xx. Пример: runway — Д-68 (красный < 9 мес, жёлтый 9–12, инвестор меняет в 6–18, флаг burn > 20%). Порог «по смыслу» без ссылки = находка.
4. **Молчаливое решение неоднозначности.** Если спецификация не задаёт поведение (EDGE-01…09 из HQ-053), код не выбирает сам — либо явная ошибка/флаг «нужно решение», либо ссылка на решение.
5. **Внешнее действие из кода.** Отправка писем, сообщений, публикация, вызов внешнего API с данными стартапов без Human Gate. В модулях S1/S3/S5 отправки наружу нет (G-4).
6. **Реальные данные в тестах или CI.** Только синтетика; LLM в CI замокан; секретов в коде и workflow нет.
7. **Тихий успех.** Функция возвращает «успех», не проверив результат записи (запись ≠ сделано, Q-066).

## 2. Уровень риска (ставит ревьюер по изменению, не по автору)

| Уровень | Что | Кто одобряет |
|---|---|---|
| Низкий | Документы, тесты, шаблоны текстов, промпты без изменения логики | Зелёный CI + ревью ИИ без открытых находок + MOS Tech |
| Средний | Обычная логика модулей S1/S3/S5, новые эндпоинты без auth-изменений | MOS Tech |
| Высокий | Защищённые пути (раздел 3) | MOS Tech + Борис |

Одобрение ИИ никогда не заменяет одобрение человека. Новый коммит после одобрения → одобрение заново.
Кто дал агенту команду на PR — отвечает за PR как автор.

## 3. Защищённые пути (всегда человек)

- `db/migrations/`, `scripts/hq018_migrate.py` — схема и миграции
- `app.py` — авторизация, сессии, инвайты, admin
- `s1_intake/scoring.py`, `s1_intake/methodology.yaml`, `s1_intake/working_values.yaml` — ядро скоринга и веса (Р-9)
- `s1_intake/llm.py` — вызов внешней модели (данные уходят наружу; Q-049)
- `.github/workflows/`, `Dockerfile`, `docker-compose.yml`, `.env.example` — CI, сборка, окружение, секреты
- `REVIEW.md`, `CLAUDE.md`, `.github/CODEOWNERS` — сами правила

## 4. Формат находок

- Начинай со счёта: «Находок: N (важных K)». Если чинить нечего — так и напиши одной строкой.
- Каждая находка: файл и строка + почему это провал по разделу 1. Догадка по имени функции без чтения кода — не находка.
- Метки: **Важно** / **Мелочь** / **Было до PR**. Мелочей не больше 3 на PR.
- Стиль, переименования, «можно красивее» — не писать.
- Класс ошибки, а не одна строка: если нашёл ошибку, проверь все такие же места в PR.
- Не повторяй находку, уже оставленную в прошлом раунде.

## 5. Раунды

- Максимум 3 раунда «ревью → правка». После третьего — остановиться и предложить автору пересмотреть подход.
- С третьего раунда ревьюить только новый diff.
- Каждая находка закрывается: исправлена или отклонена с причиной в треде. Открытая находка = PR не сливается.

## 6. Что пропускать

- `tests/golden/` — снимки; проверять только, что изменение снимка объяснено в описании PR.
- `HANDOFF.md`, `docs/` — только на ложные утверждения о статусе (раздел 1, п. 1–2).

## 7. Регрессия из наших провалов

Каждый подтверждённый дефект (PF-xx, EDGE-xx, FAILURE-xxx, инцидент на стейджинге) → тест в `tests/` с именем дефекта в названии.
Ревьюер проверяет: если PR закрывает дефект, тест на него есть и падает без исправления.
