# Стенд Nocvela: что установить и как

Версия 1 · 29.10.2026 · для Сергея Белолипецкого · основа: факты MOS Tech на 29.10 (master 54295a1), файлы репозитория Dockerfile, docker-compose.yml, .env.example, deploy/yc/*, docs/DEPLOY.md, README.md, app.py.
Значений переменных, ключей и паролей здесь нет — только имена и смысл.

## В курсе за 30 секунд
- Приложение: Flask + gunicorn, Python 3.13, база Postgres 16. В корне репозитория есть Dockerfile и docker-compose.yml.
- Машина (оценка, не из репозитория): 2 vCPU, 4 ГБ RAM, 30–40 ГБ SSD; минимум 2 vCPU / 2 ГБ.
- nginx, HTTPS и certbot в репозитории нет — их ставит Сергей. Без HTTPS вход не работает (cookie Secure). За nginx ставим TRUSTED_PROXY_COUNT=1.
- Сборка Docker-образа и живой деплой ни разу не проверялись. Демо-пользователей на стенде не создавать.

## 1. Что за приложение
- Веб-приложение на Flask (`app.py`) под gunicorn, Python 3.13. Порт внутри контейнера — 10000.
- В requirements.txt только нижние границы версий, lock-файла нет. Значит, две сборки в разные дни могут получить разные версии библиотек.
- weasyprint в образе без системных библиотек pango: отчёты отдаются в HTML, не в PDF.
- В Dockerfile нет HEALTHCHECK; gunicorn по умолчанию запускается с одним синхронным воркером. Миграции при старте контейнера не идут — это отдельный шаг.
- Что проверено: установка зависимостей на Python 3.13, импорт приложения, /health отвечает 200 (с заглушкой ИИ и SQLite). Тесты CI идут на Postgres 16.
- Вход: Google OAuth + список разрешённых адресов AUTH_ALLOWLIST. Публичны только /health, /robots.txt, /auth/*.

## 2. Важно: в репозитории два разных пути развёртывания
| Путь | Что есть в репозитории | Подходит ли для машины с Docker и nginx |
|---|---|---|
| Yandex Cloud без своей машины: Serverless Containers + Managed PostgreSQL + Lockbox | `deploy/yc/deploy.sh`, `rollback.sh`, `docs/deploy/yc-deploy.yml.proposed` (неактивный workflow), README «Развёртывание в Yandex Cloud» | нет; скрипт помечен «не проверено на живом облаке» |
| Локальная учебная среда E-1 | `docker-compose.yml`: postgres:16, шаг migrate, app на 127.0.0.1:10000, ИИ-заглушка | частично: годится как основа, но для стенда его нужно поменять (раздел 4) |

В расчёте стоимости 29.10 вариант «одна машина 2 vCPU / 4 ГБ / 40 ГБ SSD, Ubuntu 24.04, Postgres внутри, бэкапы и TLS — руками подрядчика» записан как возможный на пилот. Окончательный выбор пути НЕ ПОДТВЕРЖДЕН — его делают Борис и Сергей (вопросы в разделе 9).

## 4. Порядок установки
1. **Подготовить машину.** Обновить ОС, включить файрвол: открыть только 22, 80, 443. Вход по SSH-ключу.
2. **Поставить Docker** (Engine + compose plugin), git, nginx, certbot.
3. **Забрать код.** `git clone` репозитория borismayzel68-ai/startup-trainer-pilot-v1, перейти на коммит master, который назовут Борис и MOS Tech после код-фриза.
4. **Сделать файл окружения для стенда** (не в git, права только у владельца). Список имён — раздел 5. Пример имён — `.env.example`.
5. **Сделать отдельный compose-файл для стенда** (например `docker-compose.staging.yml`; в репозитории его нет). Отличия от `docker-compose.yml`:
   - в шаге `migrate` оставить только `python scripts/hq018_migrate.py` — **без** `hq018_seed.py` (он создаёт демо-пользователей);
   - у `app` убрать ИИ-заглушку (`S1_LLM_PROVIDER: mock`, фиктивный ключ, «мёртвый» OPENAI_BASE_URL) и брать настройки из файла окружения;
   - поставить `APP_ENV=staging`, `TRUSTED_PROXY_COUNT=1`;
   - порт приложения публиковать только на 127.0.0.1 (как сейчас), у базы — не публиковать порт вообще;
   - добавить политику перезапуска (`restart: unless-stopped`) и том для данных Postgres (он уже есть: `pgdata`);
   - обратить внимание: приложение берёт адрес базы сначала из `SESSION_DATABASE_URL`, затем из `DATABASE_URL`. Задавать одну переменную, чтобы не было двух разных адресов.
6. **Собрать и запустить.** `docker compose -f docker-compose.staging.yml build` → одноразовый `migrate` → `up -d app`. Сборка раньше не проверялась: первая сборка — это и есть проверка (чек-лист, строка 1).
7. **Настроить nginx и HTTPS** (раздел 6), выпустить сертификат certbot.
8. **Настроить Google OAuth.** В консоли Google у OAuth-клиента указать адрес возврата `https://<домен>/auth/callback`; то же значение — в AUTH_REDIRECT_URI.
9. **Проверить.** `/health` → 200; `/` без входа → перенаправление на вход; `/api/*`, `/s1/*` без входа → 401; заголовок `X-Robots-Tag: noindex`. Дальше — по документу «ТЗ-чек-лист приёмки стенда».
10. **Резервная копия базы.** В репозитории для своей машины её нет (deploy.sh опирается на бэкапы Managed PostgreSQL). Нужен регулярный дамп Postgres за пределы машины и проверка восстановления.

## 5. Переменные окружения (только имена и смысл)
### Обязательные на стенде (APP_ENV=staging)
| Имя | Смысл |
|---|---|
| APP_ENV | режим; на стенде `staging`. Включает строгие проверки при старте |
| STAGING_SYNTHETIC_ONLY | только учебные данные; если выключить — приложение не стартует |
| DATABASE_URL (или SESSION_DATABASE_URL) | адрес Postgres; SESSION_DATABASE_URL имеет приоритет |
| SESSION_SECRET | ключ подписи сессий, не короче 32 символов; без него старт падает |
| GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET | OAuth-клиент Google для входа |
| AUTH_ALLOWLIST | кто может войти: `email:роль[:scope]` через запятую. Остальным — 403 |
| AUTH_REDIRECT_URI | адрес возврата после входа Google: `https://<домен>/auth/callback` |
| PUBLIC_BASE_URL | внешний адрес стенда `https://<домен>`; без него в staging старт падает (ссылки в пакете основателю) |
| OPENAI_API_KEY | ключ ИИ-провайдера (на стенде — Yandex AI Studio) |
| OPENAI_BASE_URL | адрес OpenAI-совместимого шлюза провайдера; пустой или api.openai.com в staging — ошибка при старте |
| S1_LLM_PROVIDER | `openai` (совместимый протокол); заглушка `mock` в staging запрещена |
| S1_LLM_MODEL_ID | модель у провайдера (для Yandex — идентификатор с каталогом) |
| LLM_JSON_FORMAT | формат ответа модели; для Yandex до проверки живым вызовом в .env.example советуют `none` |
| TRUSTED_PROXY_COUNT | число прокси перед приложением; за одним nginx — `1`. Нужен, чтобы журнал видел настоящий IP и схему https |
| INVITE_CODE | код приглашения; задать своим значением — в коде есть публичное значение по умолчанию |
| S1_TILDA_WEBHOOK_KEY | ключ для приёма анкет с Tilda; без него приём отвечает 503 |
| S1_ADMIN_TOKEN | служебный токен API S1, не короче 24 символов |

### Нужные для функций пилота
| Имя | Смысл |
|---|---|
| S1_APPROVERS | персональные токены людей, которые одобряют отправку и подписывают факты (`имя:токен;…`) |
| S1_APPROVER_ROLES | роль каждого подписанта факта |
| S1_AUTO_SEND_FOUNDER_REPORT | автоотправка основателю; держать выключенной |
| S1_ANALYST_EMAILS | адреса аналитиков для уведомлений |
| S1_SMTP_* (HOST, PORT, USER, PASSWORD, FROM) | почта для уведомлений; нужна ли на пилоте — НЕ ПОДТВЕРЖДЕНО |
| FEEDBACK_WEBHOOK_URL | куда пересылать обращения кнопки «Сообщить о проблеме»; пусто — только в базу |
| S1_NOTIFY_WEBHOOK_URL | необязательный адрес уведомлений (только метаданные) |
| S1_FILE_HOST_ALLOWLIST, S1_MAX_FILE_MB, S1_MAX_DOC_CHARS | откуда и какого размера можно скачивать файлы из анкеты |
| S1_RETENTION_DAYS, SESSION_RETENTION_DAYS | сколько дней хранить заявки и сессии |
| S1_LLM_TIMEOUT_S | сколько ждать ответа ИИ |
| TRAINER_EVENT_WEBHOOK, WEBHOOK_TIMEOUT_SECONDS | куда и с каким ожиданием отправлять события завершения (см. delivery_worker.py) |

Переменные `YC_*`, `LOCKBOX_SECRET_ID`, `YC_SA_KEY_JSON` нужны только для пути Serverless (deploy.sh). Для своей машины они не нужны.

## 6. nginx и HTTPS
В репозитории конфигурации nginx нет. Что должно быть (требования кода, конкретный конфиг — на усмотрение Сергея):
- порт 80 перенаправляет на 443; сертификат — certbot (Let's Encrypt);
- nginx проксирует на `127.0.0.1:10000`;
- nginx передаёт заголовки `Host`, `X-Forwarded-For` (с добавлением адреса клиента) и `X-Forwarded-Proto https`. Приложение при TRUSTED_PROXY_COUNT=1 доверяет ровно одному прокси и берёт из этих заголовков IP и схему;
- предел размера запроса — не меньше S1_MAX_FILE_MB (загрузка файлов анкеты);
- время ожидания ответа — с запасом под ответ ИИ (S1_LLM_TIMEOUT_S).

Почему HTTPS обязателен: cookie сессии ставится с флагом Secure. По HTTP браузер её не вернёт, и вход «не держится».

Рекомендация (не проверено): в Dockerfile gunicorn запускается без `--timeout`, то есть с ожиданием по умолчанию 30 секунд и одним воркером. В `deploy/yc/web-entrypoint.sh` для облака стоит `--timeout 120`. Для стенда стоит запускать с тем же `--timeout 120` (и, возможно, несколькими воркерами). Иначе долгий ответ ИИ может обрываться. Решение — за Сергеем и MOS Tech.

## 7. Как не создать демо-пользователей
- Демо-пользователей (6 адресов `*.synth@example.test`) создают только два скрипта: `scripts/hq018_seed.py` и `scripts/seed_synthetic.py`. На стенде их не запускать.
- В `docker-compose.yml` шаг `migrate` сейчас запускает миграции **и** `hq018_seed.py`. В compose стенда оставить один `hq018_migrate.py`.
- Флага «удалить демо-пользователей» в коде нет. Если они случайно появились, удалять вручную в базе, по согласованию с MOS Tech.
- Даже если демо-пользователь есть, войти им нельзя: вход только для адресов из AUTH_ALLOWLIST через Google.
- Проверка: число пользователей с адресом на `@example.test` = 0 (чек-лист, строка 4).
- Открытый вопрос: откуда на стенде берутся 6 учебных компаний для портфеля S5, если seed не запускать, — НЕ ПОДТВЕРЖДЕНО (в репозитории есть `scripts/import_dealflow.py` и `docs/IMPORT_FORMAT.md`, но разрешён ли импорт на стенде — решает Борис).

## 8. Что НЕ ПРОВЕРЕНО
| Что | Почему важно |
|---|---|
| `docker build` | на машине MOS Tech не было Docker; образ ни разу не собирался |
| Живой деплой и работа с настоящим Postgres | проверялись только тесты CI на Postgres 16 и запуск с SQLite |
| `delivery_worker.py` | в README указан как отдельный процесс (`python delivery_worker.py`), но нигде не запускается: ни в Dockerfile, ни в compose, ни в deploy.sh. Он доставляет события завершения с повторами. Нужен ли он на пилоте — решает MOS Tech |
| `PUBLIC_BASE_URL` в `docs/deploy/yc-deploy.yml.proposed` | workflow не передаёт эту переменную, а `deploy.sh` её требует — облачный деплой через этот workflow упадёт. Для своей машины не влияет |
| Флаги `yc` в deploy.sh и названия ролей IAM | помечены «сверить на живом облаке» |
| Работа с Yandex AI Studio | живого вызова не было; формат ответа (LLM_JSON_FORMAT) не проверен |
| Нумерация миграций | два файла с номером 004; исправление — поручение от 29.10, статус НЕ ПОДТВЕРЖДЕН |
| Таймаут gunicorn под долгие ответы ИИ | см. раздел 6 |
