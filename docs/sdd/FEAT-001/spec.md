## 1. Цель и контекст

### 1.1 Проблема
На стенде 31.10 человек не может пройти путь «вошёл → понял, где он → сделал свою работу → вышел»:
обязательный код доступа, который никто не знает (D1); добавить пользователя можно только правкой настроек и перезапуском (D2);
инвестор видит экран стартапа (D3); нет «Выйти», меню и кабинета (D4); «Начать» не срабатывает (D5).

### 1.2 Ожидаемый результат
Каждый участник закрытого пилота входит под своей ролью, видит свой кабинет и только свои данные, делает одно ключевое действие роли и выходит.
**Метрика:** все роли из раздела 2, помеченные «✅», проходят сценарий UC-001…UC-004 на стенде без помощи разработчика (проход фиксируется тестом и вручную — 1 человек на роль).

### 1.3 Область действия
**Входит:** вход и приглашение, выбор роли, согласие на ПДн, общая оболочка кабинета (шапка, меню, профиль, выход), домашняя страница каждой роли, админка пользователей для владельца, удаление кода доступа.
**Не входит:** новые функции модулей S1–S7 (только вход в существующие экраны); кабинеты S4, S7, покупателя и LSM (показывается заглушка «в разработке»); оплата; публичная самостоятельная регистрация (вне объёма первого выпуска, см. FR-012); собственные пароли.

### 1.4 Термины
| Термин | Определение |
|---|---|
| Пользователь | человек с Google-аккаунтом, которому владелец выдал приглашение |
| Приглашение | запись «email + роль + область доступа», созданная администратором в админке; без приглашения войти нельзя |
| Роль | набор прав (раздел 2). У человека может быть несколько ролей |
| Область доступа (scope) | `*` — все проекты; `VC-NNN` — один проект |
| Кабинет | домашняя страница роли + общая оболочка (шапка, меню, профиль, выход) |
| Активная роль | роль, под которой человек сейчас работает; меняется переключателем в шапке |
| Фонд-арендатор (тенант) | фонд, который арендует Nocvela; все роли R1–R11 существуют внутри одного арендатора |
| Настройки арендатора | название фонда, контактный email, тексты согласия, правила фонда — задаёт фонд, в коде не зашиты |

Nocvela — мультиарендная система: каждый фонд-арендатор получает те же роли и свои настройки. Имён людей, названий фондов и адресов в требованиях, коде и шаблонах нет (решение 31.10). Техническое имя — как в коде (`auth.py`, `ACCESS_MATRIX.md`).

**Предусловия:** у человека есть Google-аккаунт; администратор создал приглашение.

**Постусловия:** человек в кабинете активной роли; вход, согласие и каждое действие записаны в журнал аудита.

## 3. Функциональные требования

### FR-001 — Вход только по приглашению из базы
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА пускать человека, если в базе есть действующее приглашение на его email (или запись в `AUTH_ALLOWLIST` — только для первого администратора).
- **Результат:** при первом входе создаётся пользователь и его роли по приглашениям.
- **Ошибки:** нет приглашения → страница «Доступ по приглашению. Напишите {контактный email из настроек арендатора}» (не JSON), запись deny в аудит.
- **AC:** AC-001, AC-002

### FR-002 — Администратор управляет доступом без перезапуска
- **Приоритет:** Must (закрывает D2)
- **Описание:** Администратор ДОЛЖЕН в админке: пригласить (email, роль, область доступа), изменить роль, заблокировать, разблокировать. Изменение действует со следующего запроса пользователя, без правки настроек и перезапуска.
- **Бизнес-правила:** выдавать роль `owner` может только администратор; заблокировать самого себя нельзя; каждое действие — строка в аудите (кто, кому, что).
- **AC:** AC-003, AC-004

### FR-003 — Код доступа не нужен вошедшему пользователю
- **Приоритет:** Must (закрывает D1)
- **Описание:** Поле «Код доступа» ДОЛЖНО исчезнуть из анкеты S1. Вход по приглашению уже подтверждает право доступа.
- **AC:** AC-005

### FR-004 — Согласие на ПДн до первого входа
- **Приоритет:** Must (уже есть: `/consent`, `pdn_consent`)
- **Описание:** Без действующего согласия вход не начинается. В профиле пользователь видит своё согласие и может его отозвать; после отзыва — выход и запрет входа до нового согласия.
- **AC:** AC-006

### FR-005 — Выбор активной роли
- **Приоритет:** Must (закрывает D3)
- **Описание:** После входа система ДОЛЖНА открыть кабинет активной роли. Одна роль → сразу её кабинет. Несколько ролей → экран «Выберите, как вы работаете сейчас» + переключатель в шапке.
- **Бизнес-правила:** активная роль хранится в сессии; права проверяются по всем ролям пользователя, а показ экранов — по активной (ПРЕДЛОЖЕНИЕ; альтернатива — права только активной роли, ВОПРОС Q-001).
- **AC:** AC-007, AC-008

### FR-006 — Общая оболочка кабинета
- **Приоритет:** Must (закрывает D4)
- **Описание:** На каждой странице ДОЛЖНЫ быть: шапка (Nocvela · имя · активная роль · переключатель ролей), меню роли, «Профиль», «Сообщить о проблеме», «Выйти».
- **AC:** AC-009

### FR-007 — Профиль
- **Приоритет:** Must
- **Описание:** Страница «Профиль»: имя и email (из Google), роли и области доступа, согласие на ПДн (дата, отозвать), «Выйти». Смены пароля нет — пароль хранит Google (собственных паролей система не хранит, 152-ФЗ: минимум данных). РЕШЕНО кодом.
- **AC:** AC-010

### FR-008 — Выход
- **Приоритет:** Must
- **Описание:** «Выйти» завершает сессию и ведёт на страницу входа; повторный «назад» в браузере не открывает данные.
- **AC:** AC-011

### FR-009 — Домашняя страница каждой роли
- **Приоритет:** Must
- **Описание:** Для каждой роли со статусом ✅ — своя домашняя страница с меню (раздел 4). Роли ⚪ видят страницу «Кабинет в разработке: что будет и когда» без данных.
- **AC:** AC-012…AC-016

### FR-010 — Основатель видит только свой проект и может начать работу
- **Приоритет:** Must (закрывает D5)
- **Описание:** Основатель с областью доступа VC-NNN открывает анкету S1, где номер проекта уже подставлен и не редактируется; «Начать» создаёт сессию тренажёра. Любая ошибка показывается текстом над кнопкой, не молча.
- **Ошибки:** у роли нет права начать → «У вашей роли нет доступа к анкете. Обратитесь к администратору».
- **AC:** AC-013, AC-017

### FR-011 — Администратор видит записи базы
- **Приоритет:** Should
- **Описание:** Раздел «Данные» в админке: пользователи, приглашения, проекты (startups), сессии тренажёра, журнал аудита — таблицы с поиском, только чтение. Правка данных — только через функции модулей.
- **AC:** AC-018

### FR-012 — Заявка на доступ («Кто вы?»)
- **Приоритет:** Could, **вне объёма первого выпуска**
- **Описание:** Человек без приглашения выбирает «Я — стартап / инвестор / эксперт / покупатель», даёт согласие, оставляет заявку; администратор одобряет → создаётся приглашение. До одобрения данных он не видит.
- **Почему не сейчас:** закрытый пилот (решение 14.10); самостоятельный выбор роли без одобрения дал бы доступ к данным фонда.

## 3a. Требования, перенесённые из версии #117 (не противоречат v0.2)

Источник: прежняя версия `specs/FEAT-001-vhod-i-registraciya/` (теперь заглушка). Что противоречило v0.2 (источник допуска — только `AUTH_ALLOWLIST`, однофондовая модель, запрет схемы, имена людей) — не переносилось, v0.2 главнее.

### FR-013 — Вход начинается только после согласия (из #117 FR-001)
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА не отправлять человека в Google, пока в сессии нет неотозванного согласия; вместо этого — редирект на `/consent`. Вход Google не настроен → 503 `oauth_not_configured`, человеку показывается текст, а не JSON.
- **Основание:** ФАКТ `auth.py:210-233` (сверить перед работой). **AC:** AC-019.

### FR-014 — Почта согласия совпадает с почтой Google (из #117 FR-003)
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА отказать во входе, если почта в записи согласия не совпадает с почтой аккаунта Google (403 `consent_email_mismatch`, запись в аудит). Согласие отозвано до возврата от Google → 403 `consent_required`.
- **Основание:** ФАКТ `auth.py:268-274`. **AC:** AC-019.

### FR-015 — Понятные страницы при любом отказе входа (из #117 FR-004)
- **Приоритет:** Must
- **Описание:** При любом отказе входа браузер получает страницу с понятным текстом и действием («вернуться к согласию», «написать {контактный email из настроек арендатора}»), а не сырой JSON. Коды (`oauth_failed`, `not_in_allowlist`, `consent_required`, `consent_email_mismatch`) и HTTP-статусы не менять (контракт); JSON остаётся для запросов не из браузера. В тексте нет внутренних деталей и чужих почт. Тексты — ПРЕДЛОЖЕНО, утверждает владелец продукта.
- **AC:** AC-019.

### FR-016 — Журнал входов, отказов и выходов (из #117 FR-006)
- **Приоритет:** Must
- **Описание:** Каждый вход, отказ и выход пишется в аудит (кто, когда, результат, причина) без персональных данных сверх почты. Просмотр — `GET /admin/audit`.
- **AC:** AC-019.

### FR-017 — Текст согласия по роли (из #117 FR-008)
- **Приоритет:** Should
- **Описание:** Система ДОЛЖНА уметь показывать текст согласия, привязанный к роли/потоку, и записывать версию показанного текста. Сами тексты — решение юриста (Q-B8), в коде не придумывать; сейчас один файл с пометкой «Черновик — юрист проверит». Реализация механизма — после получения текстов.

### FR-018 — Диагностика отказа входа на стенде (#114) (из #117 FR-009)
- **Приоритет:** Must
- **Описание:** Должен существовать письменный порядок поиска причины неработающего входа по журналу и настройкам (только названия настроек). Порядок:
  1. `GET /health` отвечает; приложение на HTTPS (Secure-cookie).
  2. `GET /auth/login` без согласия → `/consent`; с согласием → Google или 503 `oauth_not_configured` (не заданы `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`).
  3. Ошибка redirect_uri: сравнить `AUTH_REDIRECT_URI` с адресом в консоли Google (`…/auth/callback`).
  4. Запись аудита `login deny`, поле `detail`: `oauth_state_or_error`, `token_exchange_failed`, `id_token_invalid`, `not_in_allowlist`, `pdn_consent_revoked`, `pdn_consent_email_mismatch` (ФАКТ `auth.py:249-273`).
  5. Логи приложения: «OAuth: обмен кода не удался» (`auth.py:254`).
  6. Секрет неверен/утёк → Q-B3. Результат: одна строка «причина: …, подтверждено записью журнала от <время>».

### Q-B3 — признаки возможной утечки секрета входа Google (из #117)
Решение о перевыпуске — за владельцем продукта, остаётся открытым. Проверять без чтения значения (НЕ ПОДТВЕРЖДЕНО — это перечень проверок, не вывод): (1) значение когда-либо попадало в чат, issue, PR, комментарий, скриншот, журнал; (2) ИИ-ассистент разработчика имел доступ к файлу окружения или переменным стенда; (3) значение в истории git или в `.env` вне исключений; (4) вместо значения вставлен текст комментария (закрыто проверкой старта `staging_guard.py`, PR #107); (5) `oauth_failed` в журнале без объяснимой причины; (6) в консоли Google — использование клиента, которого никто не делал; (7) секрет лежит в файле на сервере с общим доступом. Значение секрета не писать нигде.

### Критерии приёмки к перенесённым FR
- **AC-019 (FR-013…FR-016):** Given нет согласия — When `GET /auth/login` — Then редирект на `/consent`. Given почта согласия ≠ почте Google — Then отказ с понятной страницей и записью аудита; коды/статусы прежние.
- **AC-020 (FR-018):** порядок диагностики воспроизводим, результат — причина со ссылкой на запись журнала.

## 5. Сценарии использования

### UC-001 — Первый вход приглашённого
**Актор:** любой приглашённый. **Предусловия:** есть приглашение.
1. Человек открывает стенд → видит «Войти через Google».
2. Система показывает согласие на ПДн → человек ставит галочку.
3. Google-вход → система находит приглашение, создаёт пользователя и роли.
4. Одна роль → кабинет роли; несколько → выбор роли (FR-005).
**Альтернативные:** A1 согласие уже есть → шаг 2 пропускается.
**Ошибочные:** E1 нет приглашения → страница «Доступ по приглашению»; E2 заблокирован → «Доступ приостановлен, обратитесь к администратору»; E3 email согласия ≠ email Google → «Согласие дано на другой адрес», повторить согласие.

### UC-002 — Администратор приглашает и блокирует
1. Администратор → «Пользователи» → «Пригласить»: email, роль, область доступа (для основателя — VC-NNN обязательно).
2. Система сохраняет приглашение, пишет аудит, показывает строку в списке.
3. Блокировка: «Заблокировать» → со следующего запроса пользователь получает «Доступ приостановлен».
**Ошибочные:** E1 email некорректен → подсказка; E2 основатель без проекта → «Укажите проект VC-NNN»; E3 попытка заблокировать себя → запрет.

### UC-003 — Основатель проходит тренажёр S1
1. Основатель входит → «Мой проект» → «Анкета».
2. Заполняет поля (номер проекта уже стоит), даёт согласие на обработку материалов → «Начать».
3. Система создаёт сессию → вопросы тренажёра → карта готовности.
**Ошибочные:** E1 незаполненное поле → подсветка поля и текст; E2 нет права → понятный текст (FR-010).

### UC-004 — Пользователь с двумя ролями переключается и выходит
1. Пользователь с ролями R1 и R2 входит → выбирает «Руководитель фонда» → «Сегодня».
2. Переключатель в шапке → «Администратор» → «Пользователи».
3. «Выйти» → страница входа.

## 6. Данные и интерфейсы

### 6.1 Модель данных (новое)
| Объект/поле | Тип | Обязательность | Ограничения |
|---|---|---|---|
| access_invites.email | text | Да | нижний регистр, валидный email |
| access_invites.role | text | Да | одна из ролей таблицы `roles` |
| access_invites.scope | text | Да | `*` или VC-NNN; для `founder` — только VC-NNN |
| access_invites.invited_by | text | Да | email администратора |
| access_invites.created_at / revoked_at | timestamptz | Да / Нет | revoked_at ≠ null → приглашение не действует |
| users.blocked_at | timestamptz | Нет | ≠ null → вход и запросы запрещены |
| session.active_role | строка в сессии | Нет | одна из ролей пользователя |

### 6.2 Интерфейсы
Подробно — `plan.md` §5: `GET /` (редирект в кабинет), `GET/POST /role`, `GET /profile`, `GET /admin/users`, `POST /admin/users/invite`, `POST /admin/users/<id>/block|unblock`, `GET /admin/data/<table>`.

### 6.3 Состояния пользователя
| Исходное | Событие | Новое | Побочные эффекты |
|---|---|---|---|
| нет | приглашение создано | приглашён | аудит `invite` |
| приглашён | первый вход с согласием | активен | создан user + role_grants |
| активен | блокировка | заблокирован | аудит `block`, запросы → 403 |
| заблокирован | разблокировка | активен | аудит `unblock` |
| активен | отзыв согласия | без согласия | выход; вход только после нового согласия |

## 9. Граничные случаи
- Email в приглашении в другом регистре → сравнение в нижнем регистре.
- Два приглашения на один email (разные роли) → обе роли.
- Приглашение отозвано после входа → роль отзывается на следующем запросе (как сейчас с allowlist).
- Последний администратор не может лишиться роли `owner`.
- Основатель без проекта в приглашении → приглашение не создаётся.
