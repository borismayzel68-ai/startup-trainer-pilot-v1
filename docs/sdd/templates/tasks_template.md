## 2. Общие правила исполнения

1. Прежде чем изменять код, изучи связанные требования, план, контракты и применимые правила репозитория.
2. Выполняй только текущую задачу и необходимые для неё изменения; не делай несогласованный рефакторинг.
3. Если требование неоднозначно, отсутствует контракт или есть конфликт с кодом, **остановись и задай вопрос**, зафиксировав блокер. Не придумывай бизнес-правила.
4. Соблюдай существующие архитектурные решения, соглашения об именовании и правила безопасности.
5. Добавляй или обновляй тесты, необходимые для проверки критериев приёмки.
6. Не изменяй публичные API, схемы БД, зависимости или конфигурацию безопасности без явно указанного разрешения.
7. По завершении сообщи, что изменено, какие проверки выполнены, что осталось непроверенным и какие есть риски.
8. Не отмечай задачу выполненной, если обязательные проверки не пройдены; явно сообщай о недоступных проверках.

## 5. Пример заполненной задачи

### T-004. Реализовать проверку срока действия токена восстановления пароля

**Статус:** Ready  
**Приоритет:** High  
**Тип:** Code + Test  
**Зависимости:** T-003 (модель и хранение токенов)

#### Цель и результат

Обеспечить отклонение токена восстановления пароля после истечения 15 минут с момента создания. Результат: серверная проверка срока действия и автоматические тесты.

**Вне рамок:** интерфейс отправки письма, изменение политики паролей, изменение структуры токена.

#### Источники истины

- `spec.md#FR-014` — восстановление пароля.
- `spec.md#AC-03` — просроченный токен отклоняется.
- `plan.md#token-validation` — правила проверки токенов.

#### Контекст

- Модуль: `auth/password-reset` (пример пути, уточнить по репозиторию).
- Использовать существующий механизм часов/времени, чтобы тесты не зависели от реального ожидания.
- Не раскрывать токены в логах.

#### Шаги

- [ ] Найти текущий механизм проверки токенов.
- [ ] Добавить проверку срока действия по утверждённому контракту.
- [ ] Добавить тест для действительного токена.
- [ ] Добавить тест для истёкшего токена.
- [ ] Проверить граничный момент истечения по правилу из `plan.md`.
- [ ] Выполнить тесты модуля.

#### Критерии готовности

- [ ] AC-03 подтверждён автоматическим тестом.
- [ ] Не изменены публичные контракты без согласования.
- [ ] Тесты модуля проходят.
- [ ] Представлен diff и отчёт о проверках.

#### Команды

- Unit tests: `<команда проекта>`
- Static analysis: `<команда проекта>`

## 6. Контроль качества набора задач (Task Quality Gate)

Перед передачей задач ИИ-агенту проверьте:

- [ ] Каждая задача имеет измеримый конечный результат.
- [ ] Все задачи ссылаются на утверждённые требования и/или технический план.
- [ ] У каждой задачи есть ясные границы и критерии готовности.
- [ ] Зависимости не содержат циклов и позволяют определить порядок выполнения.
- [ ] Не осталось требований, для которых отсутствуют задачи реализации или проверки.
- [ ] Нет избыточного дублирования задач.
- [ ] Критические изменения API, БД и безопасности явно обозначены.
- [ ] Проверки можно выполнить в доступном окружении или ограничения зафиксированы.
- [ ] Объём каждой задачи позволяет агенту выполнить её в управляемом контексте.
- [ ] Неопределённости и блокеры вынесены на согласование.
