## 1. Цель и контекст

### 1.1 Проблема
На стенде вход через Google не работает (#114: причина **НЕ ПОДТВЕРЖДЕНА**). Кроме того: нет видимой кнопки «Выйти» (адрес выхода есть); порядок «кто вы» при регистрации не определён; текст согласия один на всех, а не по ролям. Для Сергея и его ИИ нет единого описания, как должен работать вход.

### 1.2 Ожидаемый результат
Допущенный человек: отмечает согласие → входит через Google → попадает в свой кабинет; не допущенный или с другой почтой получает понятное сообщение; любой вошедший может выйти. Метрика: сценарии AC-001…AC-008 проходят на стенде; вход под тестовой допущенной синтетической почтой работает.

### 1.3 Область действия
**Входит:** вход через Google; страница согласия; сверка почты согласия и почты Google; список допущенных почт; выход; порядок «кто вы»; тексты согласия по ролям (только механизм подстановки, не сами тексты); поиск причины #114.  
**Не входит:** кабинеты и меню (FEAT-002); анкета «Начать» (FEAT-003); панель администратора (FEAT-004); тексты согласий (решение юриста); смена способа входа; пароли.

### 1.4 Термины
| Термин | Определение |
|---|---|
| Список допущенных почт | Настройка `AUTH_ALLOWLIST`, записи `почта:роль[:кейс]` (ФАКТ `auth.py:35-52`) |
| Согласие | Отметка о согласии на обработку персональных данных на `/consent` с записью почты, версии текста, времени, IP (ФАКТ `pdn_consent/blueprint.py:112-134`) |
| Роль | Один из 8 кодов (ФАКТ `auth_store.py:14-18`) |
| Грант | Выдача роли пользователю с областью (scope) (ФАКТ `auth_store.py:102-105`) |
| Кейс (scope) | `*` = все или ID проекта (ФАКТ `docs/ACCESS_MATRIX.md:14-16`) |

## 3. Функциональные требования

### FR-001 — Вход начинается только после согласия
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА не отправлять человека в Google, пока в этой сессии нет неотозванного согласия; вместо этого перенаправлять на `/consent`.
- **Условия:** запрос `GET /auth/login`.
- **Входные данные:** сессия браузера с `pdn_consent_id`.
- **Результат:** редирект на `/consent` или на Google.
- **Бизнес-правила:** ФАКТ `auth.py:226-230`, `auth.py:210-223`.
- **Ошибки и исключения:** вход Google не настроен → 503 `oauth_not_configured` (ФАКТ `auth.py:231-233`); ПРЕДЛОЖЕНО показывать человеку текст, а не JSON.
- **Связанные критерии приёмки:** AC-001

### FR-002 — Вход только для почт из списка допущенных
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА пускать только почты из списка допущенных и не создавать пользователя для остальных.
- **Условия:** возврат от Google на `GET /auth/callback`.
- **Входные данные:** почта из Google (подтверждённая).
- **Результат:** сессия и гранты ролей из списка, либо отказ 403 `not_in_allowlist`.
- **Бизнес-правила:** почта сравнивается в нижнем регистре; запись с неизвестной ролью пропускается (ФАКТ `auth.py:35-48`, `264-267`). Удаление почты из списка отзывает доступ на следующем запросе (ФАКТ `auth.py:99-104`).
- **Ошибки и исключения:** отказ пишется в журнал (ФАКТ `auth.py:266`).
- **Связанные критерии приёмки:** AC-002, AC-003

### FR-003 — Почта согласия совпадает с почтой Google
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА отказать во входе, если почта в записи согласия не совпадает с почтой аккаунта Google.
- **Условия:** `callback`, почта в списке допущенных, согласие есть.
- **Результат:** 403 `consent_email_mismatch` и запись в журнал.
- **Бизнес-правила:** ФАКТ `auth.py:268-274`; подсказка на странице согласия — ФАКТ `templates/consent.html:43`.
- **Ошибки и исключения:** согласие отозвано до возврата от Google → 403 `consent_required` (ФАКТ `auth.py:269-271`).
- **Связанные критерии приёмки:** AC-004

### FR-004 — Понятные сообщения при отказе входа
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА при любом отказе входа показывать человеку страницу с понятным текстом и действием («вернуться к согласию», «написать Борису»), а не сырой JSON.
- **Условия:** любой отказ в `login`/`callback`.
- **Бизнес-правила:** сейчас отказы возвращают JSON с кодами `oauth_failed` (400/502), `not_in_allowlist`, `consent_required`, `consent_email_mismatch` (ФАКТ `auth.py:250,256,263,267,271,274`). Коды и HTTP-статусы **не менять** (контракт). ПРЕДЛОЖЕНО: для запросов браузера (`Accept: text/html`) показывать страницу; JSON оставить для остальных. Тексты сообщений — ПРЕДЛОЖЕНО, утверждает Борис.
- **Ошибки и исключения:** в тексте не раскрывать внутренние детали и чужие почты.
- **Связанные критерии приёмки:** AC-005

### FR-005 — Выход из системы
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА давать вошедшему кнопку «Выйти», которая вызывает `POST /auth/logout` с токеном CSRF и возвращает на страницу входа/согласия.
- **Бизнес-правила:** адрес выхода есть (ФАКТ `auth.py:286-291`); в шаблонах кнопки нет (ФАКТ: поиск «logout»/«Выйти» по `templates/` и `app.py` совпадений не дал; НЕ ПОДТВЕРЖДЕНО для файлов вне `templates/`). Выход требует токен CSRF (ФАКТ `auth.py:175-176`, `index.html:26-27`).
- **Ошибки и исключения:** старая копия cookie действует до 12 ч после выхода (ФАКТ `docs/reports/STAND_CHECK_2026-10-30.md:45`) — не решаем в этой функции, фиксируем как риск.
- **Связанные критерии приёмки:** AC-006

### FR-006 — Журнал входов и отказов
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА записывать каждый вход, отказ и выход (кто, когда, результат, причина) без персональных данных сверх почты.
- **Бизнес-правила:** ФАКТ `auth.py:88-89`, `auth_store.py:117-120`; просмотр — `GET /admin/audit` (ФАКТ `app.py:736-743`).
- **Связанные критерии приёмки:** AC-007

### FR-007 — Порядок регистрации ролей («кто вы»)
- **Приоритет:** Must
- **Описание:** ПРЕДЛОЖЕНО: роль человека определяется списком допущенных почт (как сейчас), а не выбором самим человеком; экран «Кто вы» допустим только как справка/выбор вида согласия, не выдаёт прав.
- **Бизнес-правила:** ФАКТ: роли выдаются из списка при входе (`auth.py:275-277`); на странице согласия два потока — `s1_intake` («Отправить заявку») и `investor_login` («Войти как инвестор») (ФАКТ `pdn_consent/blueprint.py:23`, `consent.html:49-50`); экрана выбора остальных ролей нет (ФАКТ: в `consent.html` кнопок под другие роли нет). Окончательно — Q-B6.
- **Ошибки и исключения:** до ответа Борисом на Q-B6 новый выбор ролей не реализовывать.
- **Связанные критерии приёмки:** AC-008

### FR-008 — Текст согласия по каждой роли
- **Приоритет:** Should
- **Описание:** Система ДОЛЖНА уметь показывать текст согласия, привязанный к роли/потоку, и записывать версию показанного текста.
- **Бизнес-правила:** сейчас один файл текста (ФАКТ `pdn_consent/blueprint.py:20`, `38-40`) с пометкой «Черновик — юрист проверит» (ФАКТ `consent.html:27`). **Сами тексты — решение юриста; в коде не придумывать** (Q-B8). Реализация механизма — после получения текстов.
- **Связанные критерии приёмки:** AC-009

### FR-009 — Диагностика отказа входа на стенде (#114)
- **Приоритет:** Must
- **Описание:** Должен существовать письменный порядок поиска причины, по которой вход на стенде не работает, по журналу и настройкам (только названия настроек).
- **Связанные критерии приёмки:** AC-010

### FR-010 — Список допущенных ведёт администратор без пересборки
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА позволять администратору добавить человека в список допущенных и заблокировать его без правки настроек, пересборки проекта и перезапуска; новый человек входит сразу.
- **Бизнес-правила:** ФАКТ: сейчас список берётся из настройки окружения `AUTH_ALLOWLIST` (`auth.py:51-52`; `.env.example:20`); чтобы добавить человека, правят настройку и перезапускают приложение (ЗАЯВЛЕНИЕ ИСТОЧНИКА: Сергей, звонок 31.10: «правим настройки, пересобираем, перезапускаем»). Удаление из списка уже отзывает доступ на следующем запросе (`auth.py:99-104`) — это поведение сохранить. Решение Бориса 31.10 (Q-B2): доступ определяется входом Google и этим списком.
- **Ошибки и исключения:** неизвестная роль или формат — отказ с понятным сообщением, запись не создаётся; каждое добавление/блокировка — в журнал (кто, кого, какая роль; без лишних персональных данных).
- **Хранение:** где хранить список (новая таблица, существующая `users`/`grants`) — **ПРЕДЛОЖЕНО, решение по схеме данных за Борисом/MOS Tech** (Q-005); без него не реализовывать. Интерфейс администратора — FEAT-004 FR-007.
- **Связанные критерии приёмки:** AC-011

## 4. Сценарии использования

### UC-001 — Вход допущенного инвестора
**Актор:** инвестор. **Предусловия:** почта в списке с ролью `investor`.

**Основной поток:**
1. Открывает `/consent`, вводит почту, отмечает согласие, нажимает «Войти как инвестор».
2. Система записывает согласие, сохраняет его в сессии, перенаправляет на `/auth/login` (ФАКТ `blueprint.py:125-130`).
3. Google, выбор аккаунта (ФАКТ `auth.py:236-240`); возврат на `/auth/callback`.
4. Система проверяет токен, список, согласие, почту; создаёт сессию (ФАКТ `auth.py:257-283`).
5. Открывается `/` (кабинет).

**Альтернативные потоки:**
- A1: нет согласия в сессии → редирект на `/consent`.

**Ошибочные потоки:**
- E1: не в списке → 403 `not_in_allowlist` → страница с объяснением (FR-004).
- E2: почта Google ≠ почта согласия → 403 `consent_email_mismatch` → предложить повторить с той же почтой.
- E3: Google вернул ошибку/неверное состояние → 400 `oauth_failed`; обмен кода не удался → 502 `oauth_failed`.

**Постусловия:** сессия 12 ч; записи в журнале.

### UC-002 — Выход
**Актор:** любой вошедший. Нажимает «Выйти» → `POST /auth/logout` с CSRF → сессия очищена → страница входа.  
**Ошибочный поток:** E1: нет токена CSRF → 403 `csrf` (ФАКТ `auth.py:175-176`) → обновить страницу.

### UC-003 — Отзыв согласия
**Актор:** человек, давший согласие. Нажимает «Отозвать согласие» на `/consent`; отзыв только своего (ФАКТ `blueprint.py:93-103`, `137-154`). Чужое → 403 `consent_not_yours`.

## 8. Критерии приёмки и тестовые примеры

### AC-001 — Без согласия вход не стартует
**Связанное требование:** FR-001  
**Given:** новая сессия без согласия. **When:** `GET /auth/login`. **Then:** редирект на `/consent`.  
**Тестовые данные:** позитив — после согласия редирект на Google; негатив — без согласия; граница — согласие отозвано.  
**Способ проверки:** автоматический тест

### AC-002 — Почта из списка входит
**Связанное требование:** FR-002. **Given:** почта в списке, согласие на ту же почту. **When:** callback с валидным токеном (обмен кода подменён в тесте). **Then:** сессия, роли из списка, запись `login allow`.  
**Способ проверки:** автоматический тест

### AC-003 — Почта вне списка не входит
**Связанное требование:** FR-002. **Given:** почта вне списка. **When:** callback. **Then:** 403 `not_in_allowlist`, пользователь не создан, запись `deny`; человек видит понятную страницу.  
**Способ проверки:** автоматический тест + ручная

### AC-004 — Разные почты
**Связанное требование:** FR-003. **Given:** согласие на `a@example.test`, Google `b@example.test`, обе в списке. **When:** callback. **Then:** 403 `consent_email_mismatch`. Регистр букв не влияет.  
**Способ проверки:** автоматический тест

### AC-005 — Понятные сообщения
**Связанное требование:** FR-004. **Given:** любой из 6 отказов. **When:** запрос браузера. **Then:** страница на русском с причиной и шагом; в JSON-запросе коды и статусы прежние; в тексте нет секретов и чужих почт.  
**Способ проверки:** автоматический тест + ручная

### AC-006 — Выход
**Связанное требование:** FR-005. **Given:** вошедший. **When:** нажимает «Выйти». **Then:** `POST /auth/logout` с `X-CSRF-Token`, сессия очищена, `/` ведёт на вход; без токена — 403.  
**Способ проверки:** автоматический + ручная

## 9. Граничные случаи и обработка ошибок

- **Пустые/некорректные значения:** почта не по формату или длиннее 320 → «Укажите email» (ФАКТ `blueprint.py:72-76`); запись списка без роли/с неизвестной ролью пропускается (ФАКТ `auth.py:43-45`); `code` или `state` пустые → 400.
- **Повторные запросы:** повторное согласие — новая строка журнала (НЕ ПОДТВЕРЖДЕНО, как считается дубль); `ensure_grant` не дублирует грант (ФАКТ `auth_store.py:102-105`).
- **Тайм-ауты:** Google недоступен → 502 `oauth_failed`, таймаут 10 с (ФАКТ `auth.py:65-70`, `252-256`).
- **Частичный успех:** согласие записано, но вход не удался → согласие остаётся; повторить вход можно.
- **Авторизация:** вошёл, но роли нет → 403 с записью в журнал (ФАКТ `auth.py:154-158`).
- **Конкурентность:** состояние `oauth_state` хранится в сессии; два параллельных входа в одном браузере могут затереть друг друга (НЕ ПОДТВЕРЖДЕНО).
- **HTTP вместо HTTPS:** cookie Secure не вернётся, вход «не держится» (ФАКТ `03_Stend…md:103`).
