## 1. Цель и контекст

### 1.1 Проблема
На звонке 31.10 Сергей показал как **образец** панель администратора из своего проекта **ISOBZ Assistant** (его воронки, клиенты из Tilda и Telegram): список пользователей, поиск, создание, блокировка и активация — без пересборки (ЗАЯВЛЕНИЕ ИСТОЧНИКА, запись звонка; сам проект мы не видели). Это отдельный проект Сергея, не стенд Nocvela; его данные к стенду отношения не имеют.

В Nocvela сейчас нет интерфейса управления пользователями: есть только два адреса `GET /admin/sessions` и `GET /admin/audit` (ФАКТ `app.py:730-743`), а список допущенных — настройка окружения `AUTH_ALLOWLIST`, её правка требует перезапуска (ФАКТ `auth.py:51-52`). Ограничение проекта: до уведомления РКН на стенде только синтетические данные (ФАКТ `CLAUDE.md`, раздел «Диспетчер кода»).

### 1.2 Ожидаемый результат
**Цель:** админка Nocvela по образцу той, что Сергей показал в ISOBZ Assistant: список пользователей, поиск, создать, заблокировать или активировать — без пересборки. Панель доступна только назначенным людям, не показывает персональные данные без необходимости, каждое обращение к данным записано в журнал. Метрика: AC-001…AC-007 проходят; стенд стартует только с синтетическими данными (автоматический тест или скрипт, AC-005).

### 1.3 Область действия
**Входит:** кто имеет доступ; маскирование персональных данных; журнал просмотров и действий; сверка с правилом «только синтетика» и с `ACCESS_MATRIX.md`.  
**Не входит:** вход (FEAT-001); кабинеты (FEAT-002); новая функциональность управления пользователями; решение юриста о законности обработки; уведомление РКН.

### 1.4 Термины
| Термин | Определение |
|---|---|
| Панель администратора | Просмотр данных и журнала владельцем фонда: `/admin/sessions`, `/admin/audit` (ФАКТ) |
| Персональные данные (ПДн) | Данные физлица: имя, почта, ответы анкеты и т. п. Перечень для панели — НЕ ПОДТВЕРЖДЕНО, определяет юрист |
| Маскирование | Показ части значения (например, `a***@example.test`) |
| Журнал | Таблица `audit_log` (ФАКТ `auth_store.py:30-32`) |
| Синтетика | Выдуманные данные (`@example.test`, `is_synthetic`) |

## 2. Участники и предпосылки

| Роль/система | Права, обязанности, ограничения |
|---|---|
| Владелец фонда (`owner`) | Единственная роль с доступом к `/admin/sessions` и `/admin/audit`, scope только `*` (ФАКТ `app.py:730-743`, `ACCESS_MATRIX.md:45-46`) |
| Сотрудник фонда, инвестор, основатель и др. | Доступа нет: 403 и запись в журнал (ФАКТ `auth.py:189`) |
| Борис / юрист | Решают Q-B7, Q-B9 |
| Журнал | Пишется автоматически на каждый разрешённый и отказанный запрос (ФАКТ `auth.py:179,154-158`) |

**Предусловия:** вход выполнен (FEAT-001).  
**Триггер:** владелец открывает панель.  
**Постусловия:** запись в журнале; персональные данные показаны только по правилам этой спецификации.

## 3. Функциональные требования

### FR-001 — Доступ только назначенным
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА пускать в панель только роль `owner` (ПРЕДЛОЖЕНО — конкретные люди определяются списком допущенных, Q-B7), остальным отвечать 403.
- **Бизнес-правила:** ФАКТ `app.py:730-732,736-738`; матрица `ACCESS_MATRIX.md:45-46`. Роль `fund_staff` доступа не имеет — не расширять.
- **Связанные критерии приёмки:** AC-001

### FR-002 — Маскирование персональных данных в панели
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА по умолчанию показывать в панели персональные данные в маскированном виде.
- **Бизнес-правила (ФАКТ):** сейчас `GET /admin/sessions` отдаёт `list(SESSIONS.values())` целиком без отбора полей — в сессии есть `founder_name`, `founder_email`, текст `deck_text`, ответы `qa`, `description` (ФАКТ `app.py:734`, поля — `app.py:604-644`); публичный вид сессии скрывает `deck_text` и служебные поля (ФАКТ `app.py:110-115`), а админский — нет. Маскирования нет. **ПРЕДЛОЖЕНО:** показывать список полей-белый список; почту и имя маскировать; тексты анкеты и `deck_text` не показывать в списке. Точный перечень маскируемых полей и формат — решение юриста/Бориса (Q-B7).
- **Ошибки и исключения:** поле не определено → не показывать.
- **Связанные критерии приёмки:** AC-002

### FR-003 — Раскрытие немаскированных данных только по правилу
- **Приоритет:** Should
- **Описание:** Если Борис решит, что немаскированный просмотр нужен (Q-B7), Система ДОЛЖНА требовать явного действия («показать») и записывать его в журнал отдельной записью.
- **Бизнес-правила:** без решения Q-B7 не реализовывать.
- **Связанные критерии приёмки:** AC-003

### FR-004 — Журнал просмотров и действий
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА записывать в журнал каждый просмотр панели и каждое действие: кто (почта), когда, что (адрес, идентификатор записи), результат, IP; без самих персональных данных.
- **Бизнес-правила (ФАКТ):** сейчас пишется кто, время, путь, allow/deny, IP, кейс и роли (ФАКТ `auth.py:179`, `auth_store.py:117-120`); **не пишется**, какие именно записи просмотрены (нет идентификаторов). IP — только `remote_addr` (ФАКТ `auth.py:82-85`; `ACCESS_MATRIX.md:63` пишет иначе — расхождение). ПРЕДЛОЖЕНО: записывать идентификаторы просмотренных сессий в существующее поле `detail` (без изменения схемы). Срок хранения журнала — решение юриста (TBD).
- **Связанные критерии приёмки:** AC-004

### FR-005 — Только синтетические данные до уведомления РКН
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА стартовать на стенде только с синтетическими данными до уведомления РКН; это проверяется автоматически (ограничение проекта).
- **Бизнес-правила (ФАКТ):** `CLAUDE.md`: до уведомления РКН — только синтетика; на staging — `STAGING_SYNTHETIC_ONLY` (по умолчанию включён; другое значение — приложение не стартует) и проверка таблицы `users` на записи без признака `is_synthetic`, кроме почт из списка допущенных (ФАКТ `staging_guard.py:86-89,92-114,136-139`). Проверка **не покрывает** таблицу сессий тренажёра (`SESSIONS`/сессии анкет), где лежат анкеты (НЕ ПОДТВЕРЖДЕНО: нет проверки в `staging_guard.py`), работает только для Postgres (ФАКТ `staging_guard.py:97-98`) и только при `APP_ENV=staging` (ФАКТ `staging_guard.py:133-134`). **Если стенд Сергея не запущен как staging этого репозитория — защиты нет** (НЕ ПОДТВЕРЖДЕНО).
- **Ошибки и исключения:** в данных стенда найдена запись без признака синтетики → старт отказывает; не копировать такие данные в отчёты и логи, сообщить Борису.
- **Связанные критерии приёмки:** AC-005

### FR-006 — Сверка с матрицей доступа
- **Приоритет:** Must
- **Описание:** Права панели ДОЛЖНЫ совпадать с `docs/ACCESS_MATRIX.md` (строки `/admin/sessions`, `/admin/audit`: owner, только `*`); любое расхождение фиксируется.
- **Связанные критерии приёмки:** AC-006

### FR-007 — Администратор добавляет и блокирует пользователя без пересборки
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА давать администратору (роль `owner`, ПРЕДЛОЖЕНО; кто именно — Q-B7) действия «добавить человека с ролью» и «заблокировать», после которых вход нового человека и отказ заблокированному действуют без правки настроек, пересборки и перезапуска.
- **Бизнес-правила:** ФАКТ: сейчас список — настройка окружения `AUTH_ALLOWLIST` (`auth.py:51-52`), добавление требует правки настроек и перезапуска (ЗАЯВЛЕНИЕ ИСТОЧНИКА: Сергей, звонок 31.10). Логика и хранение — FEAT-001 FR-010; здесь — интерфейс и права. Права не расширять; каждое действие — в журнал `audit_log` (кто, кого, роль), без лишних персональных данных.
- **Ошибки и исключения:** не администратор — 403 + запись; неизвестная роль — отказ с понятным сообщением.
- **Связанные критерии приёмки:** AC-007

## 4. Сценарии использования

### UC-001 — Владелец просматривает список сессий
**Актор:** `owner`. **Предусловия:** вошёл.  
**Основной поток:** 1) открывает `/admin/sessions`; 2) видит список с маскированными данными; 3) в журнале появляется запись `view` с идентификаторами.  
**Альтернативные потоки:** A1: нужен немаскированный просмотр → только если решено (FR-003) и с отдельной записью в журнале.  
**Ошибочные потоки:** E1: роль не `owner` → 403, запись `deny`; E2: нет входа → 401/редирект на вход.  
**Постусловия:** журнал дополнен.

### UC-002 — Владелец просматривает журнал
`GET /admin/audit?limit=N` (1…500; не число → 400 `bad_limit`) (ФАКТ `app.py:736-743`). Запись о самом просмотре журнала пишется (ФАКТ `auth.py:179`).

### UC-003 — Обнаружены реальные данные
**Актор:** любой. Видит запись, похожую на реального клиента → не копирует → сообщает Борису.

## 5. Данные и интерфейсы

### 5.1 Модель данных
| Объект/поле | Тип | Обязательность | Ограничения | Пример |
|---|---|---|---|---|
| Сессия: `id`, `project_id`, `project_name`, `created_at`, `done` | служебные | Да | можно показывать | — |
| Сессия: `founder_name`, `founder_email` | ПДн | Да | маскировать (ПРЕДЛОЖЕНО) | `a***@example.test` |
| Сессия: `description`, `qa[].answer`, `deck_text`, `feedback` | свободный текст, возможны ПДн | Нет | не показывать в списке (ПРЕДЛОЖЕНО) | — |
| audit_log: `at, actor, action, object, result, ip, detail` | служебные | Да | без ПДн, кроме почты actor | — |

Схему не менять (ФАКТ-ограничение `AGENTS.md`).

### 5.2 Контракты API и событий
- `GET /admin/sessions` — HTML `<pre>` с JSON всех сессий (ФАКТ `app.py:734`); `GET /admin/audit?limit=` — JSON-массив журнала (ФАКТ `app.py:743`). Роль `owner`, scope `*`.
- **Совместимость:** изменение выдачи `/admin/sessions` (маскирование, белый список полей) меняет ответ — **согласовать с Борисом**; `app.py` — защищённый путь (высокий риск).

### 5.3 Состояния и переходы
| Исходное | Событие | Новое | Эффект |
|---|---|---|---|
| Закрыто | запрос `owner` | Список (маска) | запись `view allow` |
| Закрыто | запрос не `owner` | 403 | запись `view deny` |
| Список | «показать» (если решено) | Раскрыто | отдельная запись в журнале |

## 8. Критерии приёмки и тестовые примеры

### AC-001 — Доступ только владельцу
**Связанное требование:** FR-001. **Given:** пользователи всех 8 ролей и аноним. **When:** `GET /admin/sessions`, `/admin/audit`. **Then:** `owner` — 200; остальные — 403; аноним — 401; в журнале `deny`.

### AC-002 — Маскирование
**Связанное требование:** FR-002. **Given:** синтетическая сессия `anna@example.test`. **When:** `owner` открывает список. **Then:** почта и имя маскированы, `deck_text`, `description`, ответы не показаны.  
**Тестовые данные:** позитив — обычная почта; негатив — пустое значение; граница — очень длинная почта (320 символов), почта без `@`.

**Связанное требование:** FR-003. **Then:** раскрытие требует явного действия, пишет запись. Выполняется только если принято решение.

### AC-005 — Только синтетика
**Связанное требование:** FR-005. **Given:** стенд. **Then:** (а) `STAGING_SYNTHETIC_ONLY` включён; (б) тест или скрипт подтверждает: при старте нет ни одной записи пользователя/сессии без признака синтетики, иначе старт отказывает.

### AC-006 — Сверка с матрицей

## 9. Граничные случаи и обработка ошибок

- **Пустые значения:** нет почты/имени → «—», не падать.
- **Большие объёмы:** `/admin/sessions` отдаёт всё без пагинации (ФАКТ `app.py:734`); для больших баз — TBD.
- **Конкурентность:** просмотр во время удаления сессии — запись не найдена, пропустить.
- **Недоступность БД:** ошибка без деталей.
- **Журнал недоступен:** поведение TBD (Q-006).
- **Доступ к чужим данным:** не-`owner` — 403 + запись (ФАКТ `auth.py:189`).
- **Реальные данные обнаружены:** не копировать, не логировать; сообщить Борису.
