## 1. Цель и контекст

### 1.1 Проблема
В коде 8 ролей, но у каждой роли нет своего кабинета: после входа любая роль попадает на одну и ту же главную страницу (форма тренажёра основателя). Нет общей шапки (имя, роль, «Выйти», «Сообщить о проблеме») и меню. **Число кабинетов — открытый вопрос Бориса (Q-B1: 4 или 7).**

### 1.2 Ожидаемый результат
Каждый вошедший видит свой кабинет с меню и общей шапкой, и только то, что ему разрешено. Метрика: для каждой роли выбранного варианта — страница кабинета открывается, чужие страницы дают отказ; шапка есть на всех страницах.

### 1.3 Область действия
**Входит:** определение ролей и их маршрутов; общая шапка; меню; кабинеты по варианту А или Б (после Q-B1).  
**Не входит:** вход и согласие (FEAT-001); анкета «Начать» (FEAT-003); панель администратора (FEAT-004); новые роли и права; новые бизнес-функции кабинетов.

### 1.4 Термины
| Термин | Определение |
|---|---|
| Роль | Код доступа из 8 (ФАКТ `auth_store.py:14-18`) |
| Кабинет | Стартовая страница и меню для роли (или группы ролей) |
| Шапка | Верхняя полоса: имя, роль, «Выйти», «Сообщить о проблеме» |
| Рабочая страница | Страница/маршрут, уже разрешённый роли в `ACCESS_MATRIX.md` |
| Вариант А / Б | 4 или 7 кабинетов (ПРЕДЛОЖЕНО, состав ниже; сверить с опорным документом) |

## 3. Функциональные требования

### FR-001 — Общая шапка на каждой странице кабинета
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА показывать шапку с именем, ролью, кнопками «Выйти» и «Сообщить о проблеме».
- **Входные данные:** имя и роли из `GET /auth/me` (ФАКТ `auth.py:294-299`: отдаёт `email` и `grants`; имя `display_name` не отдаётся — НЕ ПОДТВЕРЖДЕНО, нужно ли расширять ответ; расширение контракта — только с согласия Бориса).
- **Бизнес-правила:** подписи ролей — из `ROLE_LABELS` (ФАКТ `auth_store.py:14-18`). «Сообщить о проблеме» уже есть (ФАКТ `templates/index.html:164-185`, `s1_intake/main.py:934-956`).
- **Ошибки и исключения:** нет имени → показывать почту.
- **Связанные критерии приёмки:** AC-001

### FR-002 — Определение стартовой страницы по роли
- **Приоритет:** Must
- **Описание:** После входа Система ДОЛЖНА открывать страницу, соответствующую роли; если у человека несколько ролей — страницу выбора кабинета (ПРЕДЛОЖЕНО).
- **Бизнес-правила:** сейчас `/` одна для всех и показывает форму тренажёра основателя (ФАКТ `app.py:317-320`). Роли без рабочих маршрутов видят общую страницу без пояснения (НЕ ПОДТВЕРЖДЕНО визуально).
- **Связанные критерии приёмки:** AC-002

### FR-003 — Меню кабинета только из разрешённого
- **Приоритет:** Must
- **Описание:** Система ДОЛЖНА показывать в меню только пункты, к которым у роли есть доступ по `ACCESS_MATRIX.md`; недоступные пункты не показывать.
- **Бизнес-правила:** права не расширять; прямой переход на чужой адрес — 403 и запись в журнал (ФАКТ `auth.py:154-158,189`).
- **Связанные критерии приёмки:** AC-003

### FR-004 — Роли без рабочих страниц
- **Приоритет:** Must
- **Описание:** Для `expert`, `signer`, `clinic`, `syndicator` Система ДОЛЖНА показывать понятную страницу «Кабинет в разработке» с шапкой, без выдуманных функций.
- **Бизнес-правила:** тексты — ПРЕДЛОЖЕНО, утверждает Борис.
- **Связанные критерии приёмки:** AC-004

### FR-005 — Вариант А: 4 кабинета (после решения Q-B1)
- **Приоритет:** Must (если выбран А)
- **Описание:** ПРЕДЛОЖЕНО: 4 кабинета для ролей с рабочими маршрутами — основателя, инвестора, сотрудника фонда, владельца фонда. Остальные 4 роли — FR-004.
- **Связанные критерии приёмки:** AC-005

### FR-006 — Вариант Б: 7 кабинетов (после решения Q-B1)
- **Приоритет:** Must (если выбран Б)
- **Описание:** ПРЕДЛОЖЕНО: 7 кабинетов = 8 ролей, где `owner` и `fund_staff` делят один «кабинет фонда» с разным набором пунктов: основатель, инвестор, фонд (owner+fund_staff), эксперт, подписант, клиника, синдикатор. **Состав не подтверждён опорным документом** — Сергей/Борис сверяют, при расхождении состав по документу Бориса главнее.
- **Бизнес-правила:** содержимое кабинетов эксперта, подписанта, клиники, синдикатора **не описано нигде в репозитории** (НЕ ПОДТВЕРЖДЕНО); без описания Борисом реализуются только как страница из FR-004.
- **Связанные критерии приёмки:** AC-006

### FR-007 — Отказ для чужого кабинета
- **Приоритет:** Must
- **Описание:** Попытка открыть чужой кабинет — 403 «Доступ запрещён» с записью в журнале (существующее поведение).
- **Связанные критерии приёмки:** AC-007

## 4. Сценарии использования

### UC-001 — Основатель входит в кабинет
**Актор:** основатель. **Предусловия:** вошёл, роль `founder`, scope — свой кейс.  
**Основной поток:** 1) открывает `/`; 2) видит шапку (имя, «Основатель», «Выйти», «Сообщить о проблеме») и меню (анкета, отчёты); 3) заполняет анкету (FEAT-003).  
**Ошибочные потоки:** E1: открыл `/fund/...` → 403, запись в журнале.

### UC-002 — Владелец фонда открывает кабинет
**Актор:** `owner`. Видит меню по разрешённым разделам (фонд, периметр, портфель, S1…); админ-раздел только `owner` (FEAT-004).

### UC-003 — Эксперт входит
**Актор:** `expert`. Видит страницу «Кабинет в разработке» с шапкой (FR-004). Прямой переход на рабочие адреса — 403.

### UC-004 — Несколько ролей
**Актор:** человек с несколькими грантами. Видит выбор кабинета (ПРЕДЛОЖЕНО) или объединённое меню. **Q-002.**

## 8. Критерии приёмки и тестовые примеры

### AC-001 — Шапка
**Связанное требование:** FR-001. **Given:** вошёл. **When:** открыл любую страницу кабинета. **Then:** видны имя (или почта), роль по `ROLE_LABELS`, «Выйти», «Сообщить о проблеме»; кнопки работают.  
**Тестовые данные:** позитив — роль с именем; негатив — нет имени; граница — несколько ролей.  
**Способ проверки:** автоматический + ручная

### AC-002 — Стартовая страница по роли
**Связанное требование:** FR-002. **Then:** каждая роль открывает свою стартовую страницу; пользователь с несколькими ролями видит выбор.  
**Способ проверки:** автоматический тест

### AC-003 — Меню по правам
**Связанное требование:** FR-003. **Then:** в меню нет пунктов, на которые у роли 403; все пункты меню открываются.  
**Способ проверки:** автоматический тест по таблице «роль × пункт» из `ACCESS_MATRIX.md`

### AC-004 — Страница «в разработке»
**Связанное требование:** FR-004. **Then:** для 4 ролей без маршрутов — страница с шапкой; нет ссылок на недоступное.  
**Способ проверки:** автоматический + ручная

### AC-005 — Вариант А
**Связанное требование:** FR-005. **Given:** решение Q-B1 = 4. **Then:** 4 кабинета, остальные роли — FR-004.  
**Способ проверки:** автоматический + ручная

### AC-006 — Вариант Б
**Связанное требование:** FR-006. **Given:** решение Q-B1 = 7. **Then:** 7 кабинетов по составу, утверждённому Борисом; для пустых — страница FR-004.  
**Способ проверки:** автоматический + ручная

### AC-007 — Чужой кабинет
**Связанное требование:** FR-007. **Then:** 403 и запись `deny` в журнале.  
**Способ проверки:** автоматический тест

## 9. Граничные случаи и обработка ошибок

- Нет имени → почта; нет ролей (все гранты отозваны) → 403 и предложение выйти.
- Несколько ролей и несколько кейсов (scope) → не смешивать данные разных кейсов (Q-002).
- Повторный вход, смена роли списком → роли читаются из БД на каждом запросе (ФАКТ `auth.py:106`).
- Роль `founder` с scope `*` на staging запрещена (ФАКТ `staging_guard.py:68-72`).
- Недоступные зависимости (БД) → страница ошибки, без утечки деталей.
- Доступ к чужим данным → 403 + журнал.
