## Обход закрыт: `POST /s2/checks` только через S6 (решение Штаба по Д-59, Claude, 26.10)
**Сделано**
- `s2_mandate/blueprint.py` — `POST /s2/checks` требует `s6_gate_id`. Допуск считает `s6_perimeter.engine.admit()` (PASS либо снятие owner с совпадающим sha256). Без id / несуществующий id / нет допуска → **409** с причиной, запись S2 не создаётся. Admin-токен правило не обходит (проверка стоит после авторизации и валидации тела, до записи).
- Дополнительно (в рамках «подмены шлюза»): `check_rub` и `instrument` в заявке должны совпадать с данными шлюза; шлюз одноразовый (после создания проверки в нём пишется `s2_check_id`, повтор → 409). В запись S2 добавлено поле `s6_gate`, как у `forward_to_s2()`.
- Порядок ответов: 401 (нет входа) → 400 (не JSON) → 422 (поля S2 не заполнены) → 409 (нет допуска S6) → 201. Логика FIT / NO_FIT / EXCEPTION и решения человека не менялись; `forward_to_s2()` не менялась.
- Тесты S2 создают проверки через фикстуру `make_gate` (пройденный S6). Не удалены и не пропущены. Новые: без id, пустой/неверный id, несуществующий id, NEEDS_EVIDENCE (в т.ч. подделка `result` в хранилище), пройденный → 201, admin без шлюза → 409, чужой шлюз (другой чек/форма сделки), данные шлюза изменены после снятия owner, id не от шлюза, одноразовость, снятие owner с верным sha256, `forward_to_s2` работает, RBAC-тест через `/s6/gates`.
- Починка теста S6 `test_s5_link_only_after_perimeter`: после #89 `reconcile()` принимает `actor=Actor(...)`, а не `role=`. Тест S6 падал на master; только тест, код не менялся.

**Что учесть**
1. Это меняет контракт `POST /s2/checks`: все клиенты, создающие проверку напрямую, должны сначала получить шлюз S6 (в репозитории других вызывающих нет).
2. Старые записи S2 без `s6_gate` остаются читаемыми и решаемыми, как раньше.
3. Валидность `evidence` по-прежнему только непустая строка (п. 4 выше).
